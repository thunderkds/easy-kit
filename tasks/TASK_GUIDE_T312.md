## Requirement (Pillar 1 — Adapt the requirement)

User, 2026-11-14, after the Supervisor built a private artifact "Easy Kit Atlas" (a map of every agent and skill on the Stage 0–5 pipeline, with a panel that lays the selected item's steps out in order): "is it possible to add this one to the detail docs, it looks good now". "The detail docs" is `site/docs.html`. The user chose a **new section after Skills**, not a replacement of `#skills`, and data **generated by a script** (T311).

**Restated intent** (Supervisor's interpretation, in the project's domain language):
> A reader of `site/docs.html` can open a new "Explorer" section, pick any agent or skill, and see what it does and its steps in order. The section reads the data block that T311 generates, so it never shows a step the kit no longer has. It follows the site's own theme and test rules.

**Out of scope** (what this task explicitly does NOT do):
- The data block and its stale check (T311, merged first).
- Any change to the existing `#agent-roles` and `#skills` sections, their text or their counts.
- A light theme, a filter box, links between items, a per-item deep link, a sticky panel, a table of "skills it uses". These are on the cut list.
- A third-party asset or a new font: the site self-hosts IBM Plex and allows nothing else.

**Depends on**: T311 — the `kit-explorer-data` block in `site/docs.html` must exist. Start T312 from `main` after T311 is merged.

**Requirement Refs**: None — kit maintenance; source is the request above.

## Approach

**Pattern reference**: the settings tool of `site/docs.html` (`#settings-tool`: the `settings-catalog` JSON block, `settings-tool-core` and `settings-tool-ui` scripts, the `st-*` classes and the `html.js` class that gates JS-only markup) for how a data block feeds a script; `#skills` (`.chips`, `.chip`, `.skill-flow`, `.flow-node`, `.step-no`) for the chip and numbered-step look. The Supervisor's private prototype of the same idea (a map and a panel) was an artifact page, with light and dark themes, Google Fonts and its own colours. Reuse its structure only, never its styles.
**Vital slice**: chips from the block, one panel, ordered steps for skills, startup and checklist for agents, the missing-data line.
**Cut list**: filter box; links between an agent and its skills; a per-item deep link; a sticky panel; the "rigor by complexity" and "skills it uses" tables; a light theme; any second script file.

The site's `test_site_visual_first.py` allows a section at most 150 words on first load, and wants one visual before the first `<details>`. The panel's content therefore appears only after a click, and the chips are the section's one visual. If a test forces a different shape, stop and report; do not weaken the test.

What T311 left for this task (found at its Stage 4): the generated block holds raw kit text. It contains words the site's own rules keep off the page: `KANBAN` (5 times), `In Progress` (2 times), and old wording such as "Phase 0" in the `compound` skill's steps. The static-page tests do not see text that a script draws at run time, but the site rule "no project state on the page" is about what a reader sees. So the section must not show a step or note that names the board (`KANBAN`, `In Progress`, a task ID). Decide in the oracle, with `qa-expert`: either the generator's data already omits such notes (a T311 follow-up, not this task), or the section shows the item's title and drops the note. Do not weaken `test_no_project_state_on_page`, and do not hand-edit the generated block. Also: the block is 77 KB and lives in the page; the section parses the block once, at load (the chips need the names at rest), and keeps the object.

Also check the story page: an older decision (T231) says a new skill goes on both `site/index.html` and `site/docs.html`. The explorer is a docs-page section; the story page changes only in its redirect id list (see the pin-test row).

Risk: Medium. It is the public docs page. The implementer renders every string with `textContent`. Security review is mandatory.
